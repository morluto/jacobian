# v0.2 specification: capability-first mathematical operations

[Documentation home](../../index.md)

- Status: Implemented alpha; normative for `0.2.0a0`
- Theme: Composable operations with explicit evidence and independent
  verification

## 1. Scope

v0.2 defines Jacobian's capability contract across its MCP server, CLI, and
Python library. Mathematical breadth is exposed through namespaced capability
IDs. The public MCP tool surface is:

```text
capability.describe
capability.invoke
```

Installed descriptors are also readable from `capability://catalog`.
Immutable materialized results are readable from `artifact://sha256/...`.

The catalog is installation-specific. Operators may add adapters without
changing the MCP surface or the kernel. Catalog membership means that a
capability is available; it does not imply recommendation, compatibility
beyond the advertised capability version, or verification authority.

## 2. Capability descriptors and discovery

`capability.describe` without a capability ID returns compact installed
discovery results. With an ID, its default `SUMMARY` view returns an
agent-facing exact projection for deciding whether the outcome fits. It omits
the complete schemas and examples while reporting their field names and
availability. `view = CONTRACT` returns the validation-equivalent input schema,
concise output and runtime summaries, validated invocation examples, and
supported domain-specific contract information. The legacy `view = COMPACT`
is the compatibility alias for that contract projection. `view = FULL` returns
the complete installed descriptor.

Every descriptor declares:

```text
descriptor version
namespaced capability ID
capability version
title and description
provider
supported EXPLORE and VERIFY modes
input and output JSON Schemas
read-only and episode-recording behavior
discovery tags
```

Capability IDs describe concrete mathematical operations, for example
`graph.search.atlas`, `graph.compute.properties`, `case.partition.finite`,
`knowledge.search`, or `lean.check`. They are not members of a closed universal
operation enum. Domain adapters own their schemas and mathematical meaning.

Callers use the small summary to judge fit, then must inspect the exact
`CONTRACT`, legacy `COMPACT`, or full descriptor before invocation. Clients
that generate bindings, validate outputs, or audit provider configuration must
request the full descriptor. Every exact projection states that one invocation
covers its supplied input or claim; repeated bounded instances do not establish
an unbounded or parameterized conclusion. Unknown IDs, unsupported modes, and
invalid payloads return actionable diagnostics rather than mathematical
conclusions.

## 3. Invocation

`capability.invoke` accepts:

```json
{
  "capability_id": "graph.compute.properties",
  "mode": "EXPLORE",
  "payload": {}
}
```

The payload must satisfy the capability's advertised input schema. The adapter
result must identify the same capability ID, capability version, and mode as
the request. Completed outputs must satisfy the advertised output schema.

Each invocation has one observable mathematical outcome. An adapter may
coordinate several backend calls when they jointly implement that outcome, but
it must not conceal material intermediate artifacts, relationships,
obligations, scope, or verification boundaries.

The two execution lanes are:

- `EXPLORE`, for retrieval, construction, computation, transformation, search,
  and proposed evidence;
- `VERIFY`, for an operation that may invoke an operator-authorized independent
  checker.

These lanes express assurance policy, not a prescribed research sequence. A
descriptor may advertise either or both.

## 4. Result contract

Every invocation returns a `CapabilityResult` with:

```text
response version
capability ID and version
requested mode
execution status
typed domain output
explicit scope when applicable
completeness and its basis
artifact relationships
open or discharged obligations
actionable diagnostics
assurance level and basis
materialized artifact URIs
optional research-episode URI
```

Execution status, input validity, mathematical conclusion, assurance,
evidence type, and completeness are separate fields. A failed invocation
cannot report verified assurance or complete coverage. A complete result must
state its exact scope.

Assurance levels are:

```text
HEURISTIC
COMPUTED
VERIFIED
```

`EXPLORE` cannot return `VERIFIED`. `VERIFIED` requires a successful `VERIFY`
invocation and a local immutable verification record. Proposed relationships
and open obligations remain visibly distinct from verified relationships and
discharged obligations.

First-class artifact references used by scope, relationships, obligations, or
verification must also appear in the result's artifact list. This lets callers
inspect and replay the evidence graph without reconstructing hidden workflow
state.

## 5. Fail-closed verification

Search, generation, retrieval, evaluation, solver output, and exact computation
produce evidence. They do not verify their own conclusions.

An operator-authorized checker may produce `VERIFIED` only when the
verification record is bound to the exact:

```text
claim
domain semantics
candidate or construction
scope
evidence or certificate
certificate format
checker identity and version
```

The kernel rejects a verified result unless its verification record exists
locally, exposes the checked evidence, and binds every projected verified
relationship, discharged obligation, and verified completeness claim.

Checkers are authorized separately from capability and plugin installation.
Search code, generators, evaluators, untrusted plugins, and callers cannot
authorize the checker that promotes their output. An independent checker must
not depend on the proposing or search implementation whose result it certifies.

`TIMEOUT`, `CANCELLED`, `ERROR`, incomplete enumeration, partial coverage, and
failure to find a witness never imply a mathematical conclusion. Negative
bounded-search conclusions require checker-backed completeness evidence over
the declared scope.

## 6. Artifacts, provenance, and replay

Materialized artifacts are immutable and content-addressed. Identity binds the
registered schema, semantics, canonicalizer version, and canonical payload.
Exact artifacts contain no JSON floating-point values. Canonical rationals are
reduced, use a positive denominator, and encode zero as
`{"num": "0", "den": "1"}`.

Verification records are immutable. Revocation prevents affected checkers from
authorizing new records; it does not silently reinterpret existing records.
Results expose provenance and artifact relationships needed to inspect or
replay their evidence.

Capabilities configured to record episodes write completed invocations to
research memory. An episode preserves the capability identity, normalized
request, result, assurance, verification record when present, artifacts,
summary, and tags. Episode retrieval preserves original assurance and does not
promote remembered results.

## 7. Adapter and domain boundary

The kernel owns:

- artifact identity and storage;
- invocation validation and execution status;
- budgets and provenance;
- assurance invariants;
- checker authorization;
- verification-record binding.

Capability adapters own external integrations and convert between domain
contracts and the common result envelope. Domain plugins own mathematical
schemas, transformations, invariants, witness meanings, and required checker
roles. Independent checker packages implement replay.

Adapters should delegate mathematics to maintained, version-pinned proof
assistants, CAS systems, solvers, optimization systems, databases, and domain
libraries when appropriate. A thin adapter preserves Jacobian's typed
artifacts and trust boundaries; it is not a mechanical wrapper for every
backend function.

## 8. Compatibility

The v0.2 shared envelope versions are:

```text
CapabilityCatalog.catalog_version = "1"
CapabilityDescriptor.descriptor_version = "1"
CapabilityRequest.request_version = "1"
CapabilityResult.response_version = "2"
```

Capability contracts are versioned independently. Experimental capabilities
may make version-breaking changes. Compatibility exists only for capability
versions explicitly supported by an installation; availability alone creates
no compatibility promise.

## 9. Conformance

A conforming v0.2 implementation must demonstrate that:

1. Catalog discovery and exact descriptor lookup report installed capability
   contracts.
2. Invocation rejects unknown IDs, unsupported modes, and schema-invalid input
   without producing a mathematical conclusion.
3. Adapter outputs are checked against capability identity and output schema.
4. Non-completed execution cannot report complete or verified results.
5. `EXPLORE` cannot return verified assurance.
6. Verified results require an authorized local record bound to all checked
   evidence and projected claims.
7. Verified relationships, discharged obligations, and verified completeness
   use that same record and expose their bound artifacts.
8. Incomplete search and absence of a witness remain non-conclusions.
9. Untrusted adapters and plugins cannot authorize checkers or alter trust
   policy.
10. Materialized artifacts and episodes retain provenance without upgrading
    assurance.

The detailed behavioral suite is
[v0.2 conformance](../conformance-v0.2.md).

## 10. Non-goals

- A universal mathematical object schema or operation taxonomy
- One top-level MCP tool for every mathematical operation
- A kernel-prescribed proof or research strategy
- Treating exact computation, solver success, or bounded search as verification
- Universal reproducibility of heuristic search trajectories
